# OFX bank-response profile

`jbt.importers.ofx.extract(data: bytes) -> OfxStatement` reads one bounded OFX XML 2.x bank statement response without fetching data or deciding financial treatment. The frozen `OfxStatement` retains bank ID, account ID and type, currency, transaction-list start/end and ledger-balance dates (both typed civil dates and their exact source tokens), optional explicitly stated boundary instants, exact balance, and a tuple of frozen `OfxTransaction` observations. Each transaction retains FITID, posted date and raw date token, exact signed amount and source scale, TRNTYPE, NAME, optional MEMO, and a positional locator. `to_extraction(statement, context: OfxContext)` serializes these observations to the existing version-1 extraction wire shape; the context requires a canonical source-scope ID, lowercase SHA-256 blob digest (64 hex characters), and importer ID. The serializer does not invent an entity, booking, opposing leg, source status token, or opening balance.

`source_anchor(context, section, locator) -> AcquiredAnchor` gives the model the same anchor as the serializer: `blob_digest=context.source_blob_digest`, `namespace=context.source_scope_id`, the extraction record's `source_section`, and its `record_locator`. Locators are format-qualified `ofx:` structural paths; transaction indices distinguish rows even if their values are identical. `source_record_id(anchor)` hashes that exact four-field anchor through the canonical `source-record` digest domain. The serializer emits it in every record's `source_record_id`, including `LEDGERBAL` in both movement-bearing and empty responses. Use `BALANCE_LOCATOR` and section `LEDGERBAL` for its anchor. Importer ID, FITID, names, amounts, and dates do not replace the anchor dimensions; a distinct blob or interpretation namespace changes the source record ID.

Transaction records use stable `event_key="transaction"`; FITID remains `external_record_id`, not a component key. The wire's `source_account_identifier` and `source_scope.source_accounts` use the stated ACCTID; a separate `source.bankid` observation preserves BANKID without smuggling it into ACCTID. The transaction's `description_as_stated` and `payee_as_stated` retain NAME, and optional MEMO is a separate `source.memo` field observation, never a fallback description. `source.trntype` and `source.accttype` field observations retain their respective source tokens. `source.dtstart` and `source.dtend` observations retain exact boundary tokens with `event_key="interval"` so a wire-only consumer can distinguish date-only from explicitly timestamped search bounds. The shared wire carries date precision with no offset or timezone for date-only values; for an explicitly stated GMT midnight, it carries second precision and the stated offset/zone. The format's date-only GMT default is not fabricated into a timestamp wire bundle.

## Supported wire subset

The accepted input is an XML 1.0 UTF-8 declaration immediately followed by the OFX processing instruction with `OFXHEADER="200" VERSION="220" SECURITY="NONE" OLDFILEUID="NONE" NEWFILEUID="NONE"`. It contains exactly one `OFX/BANKMSGSRSV1/STMTTRNRS/STMTRS`: `CURDEF`, `BANKACCTFROM` (`BANKID`, `ACCTID`, `ACCTTYPE`), `BANKTRANLIST` (`DTSTART`, `DTEND`, zero to 500 `STMTTRN`), and `LEDGERBAL` (`BALAMT`, `DTASOF`). An optional `SIGNONMSGSRSV1/SONRS` allows only `STATUS` (`CODE=0`, `SEVERITY=INFO`, optional `MESSAGE`), `DTSERVER`, `LANGUAGE`, and `FI` (`ORG`, `FID`). Optional response `TRNUID` and successful `STATUS` (`CODE`, `SEVERITY`, optional `MESSAGE`) are control metadata only.

The supported account types are `CHECKING` and `SAVINGS`; currency is three uppercase ASCII letters. Each transaction requires `TRNTYPE` (`CREDIT` with positive `TRNAMT`, or `DEBIT` with negative `TRNAMT`), `DTPOSTED`, `TRNAMT`, unique `FITID`, and `NAME`; `MEMO` is optional. This sign/type consistency is an additional *profile restriction*, not a general OFX rule: the sign of `TRNAMT`, rather than `TRNTYPE`, governs its effect. Identifiers are one to 128 ASCII letters, digits, dots, underscores, or hyphens. Amounts must be at most 32 characters of finite decimal text, with optional leading minus and no leading plus, within the existing exact-decimal capacity; normalization keeps the stated fractional scale. Transaction posted dates are exactly eight digits (`YYYYMMDD`); `DTSTART`, `DTEND`, and `LEDGERBAL/DTASOF` accept that date-only form or explicit midnight GMT (`YYYYMMDD000000[0:GMT]`). Typed `start_instant`, `end_instant`, and `balance_instant` are UTC-aware only for the explicit form and otherwise `None`. `parse_boundary(token: str) -> tuple[date, datetime | None]` applies the same parser to retained `source.dtstart`/`source.dtend` tokens; callers must require the second result to be non-`None` before claiming an explicit UTC midnight. It raises located `OfxError` for invalid or unsupported tokens. Other timestamp precisions/offsets fail rather than being coerced into boundary instants.

The transaction list starts at `DTSTART` **inclusive** and ends at `DTEND` **exclusive**. These response values describe where the server looked; they do not promise that every posted movement in the interval is present, nor require each returned transaction's `DTPOSTED` to fall within it. All returned movements are retained, including out-of-interval posted dates. `STMTTRN` is source-supported evidence of *posted* rather than pending transactions: it is finalized and reflected in `LEDGERBAL`; no artificial `status_token` is emitted. `LEDGERBAL/DTASOF` is a balance **as of one instant**, not an opening or closing interval assertion. Serialization records a point assertion (`is_complete=false`) and leaves source-scope completeness `unstated`.

For the synthetic source equation, an explicitly timestamped prior point at January 1 00:00 GMT and main point at February 1 00:00 GMT bracket the main list's January 12 and January 20 posted movements. A bound project may declare this *comparison* convention: the prior point is before those source movements; the February 1 point follows them, equivalent to a January 31 `after_last` model comparison. It must refuse that comparison when a movement is at either boundary or otherwise outside the bracket; date-only movement timestamps on January 1 are not provably after a point at the same midnight. The importer does not assign the point an opening/closing source role, move the prior source point to the model, or assert that all intervening movements were supplied. The source arithmetic equation is a consistency check over returned evidence, not a complete-interval certification. Without separate reviewed coverage evidence, coverage remains `NOT_EVALUABLE` even if this equation passes.

The [synthetic main response](../../tests/jbt/importers/fixtures_synthetic/main.ofx) has search interval `[2026-01-01 00:00, 2026-02-01 00:00)` GMT, credit FITID `credit` +20.00 on January 12 (NAME `Invented income`), debit FITID `debit` -5.00 on January 20 (NAME `Invented expense`), and ledger balance 115.00 at the February 1 boundary. The independent [prior response](../../tests/jbt/importers/fixtures_synthetic/prior.ofx) has no transactions and states 100.00 USD at the January 1 midnight boundary; both use BANKID `TESTBANK`, ACCTID `INVENTED-1`, CHECKING, and USD. Both source observations remain points. In this bound project the authored initialization is **December 31, 2025**, before the prior point, so a sink may conditionally project that January 1 source point as a beginning-of-day Beancount balance assertion against the prior-day modeled posting. This sink projection requires the explicit UTC midnight timestamp and independently established model ordering; it does not change the source point into a complete-interval assertion. `100 + 20 - 5 = 115` is a test equation over *distinct sources*, not a value derived or certified by the importer.

Unsupported content fails at extraction rather than disappearing: additional accounts/responses, pending `BANKTRANLISTP`/`STMTTRNP`, corrections/reversals, other transaction types, financial aggregates such as available balance, non-allowlisted fields or attributes, duplicate `FITID` values, non-UTF-8 or non-NFC text, malformed XML, DTD/entity declarations, comments, and extra processing instructions. Failures carry a machine-readable code and trusted structural location, never unknown element names, namespaces, or source values, without a success-shaped partial extraction. Archiving rejected bytes is the caller's responsibility.

## Resource and parser boundaries

The importer accepts at most 1,048,576 bytes (`MAX_BYTES`), depth 12 with the root at depth 1 (`MAX_DEPTH`), 500 transaction elements (`MAX_ROWS`), and 8,192 total elements (`MAX_NODES`). The standard library XML parser uses a guarded `TreeBuilder` that checks depth, transaction count, and total-node budgets before allocating the offending element; it does not build an unbounded tree and validate limits afterward. The maximum supported profile, including every optional sign-on/control field and all 500 rows with MEMO, needs 31 control/statement elements plus seven elements per transaction: 3,531 total, below the node budget. The exact header and UTF-8 checks precede parsing, and every `<!` or `<?` occurrence in the body is rejected before parser construction. No OFX or XML dependency is required.

Runtime input capture and reload reject OFX acquisition receipts exceeding `MAX_BYTES` before streaming inventory validation. Execution repeats that guard immediately before loading each source, even when extraction results are cached. The storage reader remains format-independent: `read_object` supplies the receipt's expected size to its opened-file read, which rejects a stat-size mismatch before reading payload bytes and reads at most the initial opened size plus one byte even if the file grows. Regular-file, mutation, length, and digest checks remain mandatory; retained authored records are not subject to an OFX-wide size cap, and inventory verification continues to hash evidence incrementally.

## Specification evidence

The primary source is the Financial Data Exchange [OFX Banking Specification v2.3](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX-Banking-Specification-v2.3.pdf). Its OFX file-format chapter, sections 2.2–2.3 (printed pp. 35–37), specifies the XML declaration, OFX PI, accepted 2.2 `VERSION=220`, and XML structure. Section 3.2.3 (p. 84) scopes FITID uniqueness to an account. Section 3.2.7 (pp. 87–88) defines inclusive request start, exclusive end, and response search boundaries; section 3.2.8.2 (p. 89) allows complete timestamps with GMT offsets and says date-only timestamp values default to the start of day GMT. Banking sections 11.4.2.2 (pp. 208–209) and 11.4.4 (pp. 214–215) distinguish `BANKTRANLIST` from pending `BANKTRANLISTP`, identify `LEDGERBAL/DTASOF` as the balance date, and define `STMTTRN` as posted transactions reflected in the ledger balance. Section 11.4.4.1 says amounts are signed from the customer's perspective. **OFX does not define a `before_first`/`after_last` role or establish the completeness of an arbitrary downloaded period**; the bracket comparison above is a declared bound-project convention, not a claim from the format.
