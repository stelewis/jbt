# OFX bank and card extraction profile

The installed `ofx` entry point implements `Importer.extract(bytes, ExtractionContext) -> dict`, profile `ofx-xml-bank-card`, profile version 2, extraction contract version 1. Runtime resolves installed metadata rather than importing the adapter directly. The adapter extracts evidence; the quantity model resolves explicitly bound bank/card accounts, keyed overlap, source-stated replacements/deletions and visible non-booking pending rows. Reviewed identity and statement-revision decisions belong to the model, not the adapter.

## Extraction wire and identities

`jbt.importers.ofx.extract` returns a frozen `OfxDocument` containing frozen bank/card sections and rows. `to_extraction` serializes that document through the shared extraction boundary; `jbt.extraction.encode` validates the closed schema, caller-owned source scope, retained blob digest, importer ID, and each record's canonical blob/scope/section/locator identity before fresh output can be cached. Cached output passes the same validation.

The root `source_scope.sections` replaces a single unqualified account inventory and interval. Every section retains:

- a stable `section_id`, source class `rolling`, stated institution and currency, account identifier, and exact account context;
- separately keyed evidence parts for posted movement search bounds, settled balance, available funds or credit, and any pending snapshot;
- observed membership as exact structural record locators, with completeness `unstated`.

The section ID uses the domain-separated canonical `ofx-account-section` framing of stated account kind, sign-on institution context when supplied, and account fields. Bank context requires `BANKID`, `ACCTID`, and `ACCTTYPE`, preserving optional `BRANCHID` and `ACCTKEY`. Card context requires `ACCTID` and preserves optional `ACCTKEY` and stated institution context. Response position, currency, statement dates, and resolved model account never choose the section ID. Repeated responses for the same account context are explicitly unsupported; separate distinct accounts are supported.

Records retain required nullable `source_key_domain`, `source_key`, and `source_correction` fields. Posted transactions and their field observations use domain `ofx-fitid` and the exact `FITID`. Pending rows are keyless. Duplicate posted FITIDs inside one section fail; the same FITID in another account section is valid. The correcting row keeps its own FITID, posting time, TRNTYPE, and signed amount for both replacement and deletion. A correction explicitly names the target key domain, target key, and `replace` or `delete` action. Its posting date is not revision order; extraction does not apply the correction.

Observation payloads carry required nullable `subject_source_record_id`. Transaction field, status, and raw time observations explicitly name their owning source transaction; balance time observations name their assertion. The subject uses the same source-anchor framing as the owning record and must exist in the same section. Section/account observations have no subject. Consumers associate keyless pending evidence through this reference and event key, never by parsing OFX locators or grouping null external IDs.

Every record also retains a blob-specific occurrence identity. `source_anchor(context, section_id, locator)` constructs an `AcquiredAnchor`, and `source_record_digest` names that exact blob/namespace/section/locator through the existing `source-record` domain. Locators use actual format-qualified structural paths, including one-based response and row occurrences. Reordering rows preserves account-section and source-key economic identity but changes retained occurrences. No digest of financial facts or fallback identity is used.

The generic extraction schema remains usable for price, corporate-action, and document evidence: account identifiers, institution, and currency may be absent; `observation_set` parts retain generic membership without imposing OFX movement or balance requirements. Version 1 is a pre-alpha wire, with no singleton alias or implicit upgrade.

## Posted, pending, and balance evidence

`BANKTRANLIST` retains exact `DTSTART` and `DTEND` tokens and normalized time bundles in the `posted` movement part. Start is inclusive and end exclusive. These are server search bounds, not complete-period promises, and returned posting dates need not fall inside them.

Posted `STMTTRN` requires `TRNTYPE`, `DTPOSTED`, `TRNAMT`, and FITID. `CORRECTFITID` and `CORRECTACTION` must appear together. NAME and MEMO are optional, exact descriptive UTF-8 text: padding and decomposed Unicode survive unchanged. An absent NAME stays null, not a MEMO or FITID fallback. Supported transaction types are `CREDIT`, `DEBIT`, `INT`, `DIV`, `FEE`, `SRVCHG`, `DEP`, `ATM`, `POS`, `XFER`, `CHECK`, `PAYMENT`, `CASH`, `DIRECTDEP`, `DIRECTDEBIT`, `REPEATPMT`, `HOLD`, and `OTHER`. Signed amounts are independent of TRNTYPE; extraction never classifies or reverses them.

Pending `BANKTRANLISTP` retains its required generation `DTASOF` in a distinct `pending` snapshot part. `STMTTRNP` requires initiation `DTTRAN`, TRNTYPE, and signed TRNAMT, and rejects FITID and DTPOSTED. `DTEXPIRE` is permitted only for HOLD. Initiation and expiration are separate normalized `initiated` and `expires` time roles, not invented authorization or posting dates. Pending initiation can fall outside the posted search bounds. No pending-to-posted correspondence, disappearance inference, ledger effect, or HOLD sign interpretation is supplied.

Each transaction retains its exact source structure token as `status_token` and a `source.status` observation. Root `status_mappings` declares `STMTTRN → recognized` and `STMTTRNP → pending` for event key `transaction`. These are importer profile semantics for a consuming model to merge per source scope; they do not apply revisions or decide model participation during extraction.

`LEDGERBAL` produces an incomplete `account_net`, units, point assertion with basis `ofx-ledgerbal-point`, and a separate `settled` evidence part. It is never an opening/closing interval assertion. `AVAILBAL` produces a `source_field` observation and `available` evidence part, with meaning `available_funds` for banks or `available_credit` for cards. It never asserts settled position quantity. Pending snapshots and these two balance observations retain their own DTASOF independently.

`ORIGCURRENCY` preserves CURSYM and exact CURRATE, quoted as CURDEF units per original-currency unit. Quantity resolution uses dated symbol declarations to publish `original_commodity_id`, `fx_rate_as_stated`, `fx_base_commodity_id` and `fx_quote_commodity_id` with source provenance. These are informational fields: the signed amount and booked weight remain in CURDEF, and no original amount, price, cost basis or inventory effect is derived. Conflicting keyed observations cannot silently select different currency/rate facts. `DTUSER`, `DTAVAIL`, CHECKNUM, REFNUM, SIC, PAYEEID, and EXTDNAME are retained when supplied. Economically unsupported `CURRENCY`, statement-closing `CCSTMTENDRS`, unknown aggregates, and attributes fail explicitly rather than disappearing.

## Exact values and time

Financial numbers use `ExactDecimal`, retaining canonical coefficient/value scale and stated source scale. Negative zero stays canonical zero with its original fractional precision. The numeric capacity is 96 coefficient digits and 38 fractional digits; no binary floating-point conversion or sign/type restriction is imposed. Account and transaction identifiers are strictly one to 128 ASCII letters, digits, dots, underscores, or hyphens; they are not stripped, normalized, or repaired. Source-zone names retain validated NFC key text independently of their offsets. Currency is three uppercase ASCII letters.

The verified complete OFX datetime syntax is `YYYYMMDDHHMMSS.XXX[gmt offset[:tz name]]`. Sections 3.2.8.1–2 specify date-only, whole-second, and millisecond forms, optional zone names, GMT defaults, offsets from −12 to +12, and two-decimal fractional-hour offsets. The adapter preserves the exact raw token and a frozen domain `SourceTimeObservation`: a validated proleptic Gregorian ISO date string (including year 0000), exact local clock (including lexical leap second 60), integer `offset_seconds`, precision, fractional digits, and independently stated zone. An offset of `+5.01` hours is exactly 18,036 seconds; negative equivalents are retained without rounding. A date-only token has date precision with no fabricated local time or offset. A clock without an explicit bracket uses offset zero under OFX's GMT default; its raw token retains the lexical absence. This format interpretation belongs in the adapter, not the generic temporal resolver.

Source evidence and model-resolved time are distinct contracts. Extraction's source-owned time bundles use `timestamp_offset_seconds` and source-calendar date projections, independently of financial table columns. Validation constructs `SourceTimeObservation` for every retained time bundle; generic price, corporate-action, and document extracts share the source calendar. The financial model's `TimeObservation` keeps its supported Python civil calendar, non-leap clock, and integer-minute offsets. Year-zero conversion, absent leap-second rules, and unsupported exact offsets produce scoped `source_time_interpretation_unavailable` model findings while the extraction remains valid. The independent source check reports unavailable comparisons as `not_evaluable`, even if other sections reconcile. Neither boundary drops evidence or rounds time. Hour-only and minute-only truncations are not established by the examined OFX date/datetime form table and are rejected.

## Resource and parser boundaries

Input must have an XML 1.0 UTF-8 declaration followed by the OFX PI with `OFXHEADER="200" VERSION="220" SECURITY="NONE" OLDFILEUID="NONE" NEWFILEUID="NONE"`. The root permits optional successful sign-on metadata, multiple bank `STMTTRNRS/STMTRS` responses and multiple card `CCSTMTTRNRS/CCSTMTRS` responses. Successful STATUS and response TRNUID are control metadata. Bank account types are CHECKING, SAVINGS, MONEYMRKT, CREDITLINE, and CD.

The adapter caps bytes at 1,048,576, XML depth at 12 (root depth 1), total elements at 8,192, and posted plus pending rows across all sections at 500. A guarded standard-library TreeBuilder enforces structural budgets before allocating an excess element. UTF-8 and header validation and rejection of DTD/entity declarations, comments, and extra processing instructions precede parser construction. No XML or OFX dependency, external entity access, or network access is needed.

Failures expose stable codes and trusted structural locations, never source values, unknown names, or namespaces; there is no partial-success document. Archiving rejected bytes is the caller's responsibility.

Runtime rejects receipts beyond the selected importer's declared cap before inventory reads, and retained execution checks caps even for cached results. Storage remains format-independent: an opened-file stat-size mismatch fails before reading and the reader takes at most the initial size plus one byte if a file grows. Regular-file, mutation, length, and digest checks remain mandatory.

## Quantity-model comparison

The installed [checking/card example](../../examples/checking-card/project.json) retains independent [prior points](../../examples/checking-card/prior.ofx) and a [main response](../../examples/checking-card/main.ofx). Checking reconciles `100 + 20 − 5 − 7 = 108`; card reconciles `0 − 8 + 15 − 1 = 6`. The pending −9 card row is excluded from both equations. Account bindings resolve retained scope/section IDs; a changed account number can use another binding to the same semantic account without changing its position.

Authored initialization precedes the January 1 explicit GMT midnight points but does not assign them a source opening role. Source equations require points with matching namespace, section, commodity symbol, assertion kind, scope kind, units measurement, and basis. One extract must cover their actual span; its download window may be wider. Only its explicit posted-interval members in the half-open point span participate: January 1 is inside, February 1 is outside, and both returned rows remain source evidence. A lone prior point is evidence, not an equation. A second section bound to the same modeled account cannot borrow that point. Rolling downloads never union their movement sets. Compatible scoped keys resolve one modeled event with deterministic selected and confirming occurrence support.

Date-only balances do not establish midnight points. Explicit clocks resolve in the account's civil zone under the [pinned time contract](./coverage.md#civil-dates-and-reproducibility); unresolved required conversions remain unavailable rather than becoming guessed dates. The importer never changes a source point into an opening/closing role. A conditional Beancount beginning-of-day assertion uses the explicit timestamp and independently established model ordering. Reconciliation is arithmetic over distinct evidence, not complete-interval certification. Due coverage without complete evidence fails; OFX search bounds cannot satisfy that requirement.

## Specification evidence

Primary sources are the Financial Data Exchange [OFX Banking Specification v2.3](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX-Banking-Specification-v2.3.pdf) and [companion schemas](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX.v2.3.zip). Page numbers are printed specification pages. These are format semantics, not claims that every format capability is supported.

- **Wire and time:** §§2.2–2.3 (pp. 35–37) specify XML and the 2.2 header. §§3.2.8.1–2 (pp. 89–90), inspected directly, give the complete datetime grammar, right-omitted form table, GMT default, optional zone name, fractional-hour offsets, and leap seconds. `OFX_Common.xsd/DateTimeType` is a lexical schema, not permission to reinterpret unsupported civil-time values. §3.2.7 (pp. 87–88) establishes inclusive search start and exclusive end.
- **Identity and pending:** §3.2.3 (pp. 84–85) scopes FITID to financial institution/account, independently of service provider, not a global ID or revision counter. §§11.4.4.1–2 (pp. 214–218) distinguish keyed posted STMTTRN and keyless pending STMTTRNP. Pending requires DTTRAN, permits DTEXPIRE only for HOLD (p. 218), and has no source-supplied posted correspondence. BANKTRANLISTP requires generation DTASOF (pp. 208, 212); initiation is not bounded by the posted window (p. 206). Pending is not reconciled with LEDGERBAL.
- **Corrections:** §11.4.4.1 (pp. 214–215) defines CORRECTFITID and REPLACE/DELETE. `OFX_Common.xsd` requires paired correction fields and retains TRNTYPE, DTPOSTED, TRNAMT, and the correcting row's own FITID even for deletion. The contract does not require current and target IDs to differ or default a DELETE amount. Posting time is not revision time.
- **Currency and signs:** §5.2 (pp. 105–106) defines CURRATE as default-currency units per CURSYM unit. ORIGCURRENCY means amounts were converted to CURDEF; CURRENCY means scoped amounts remain in CURSYM. §11.4.4.1 (pp. 214–215) defines customer-perspective TRNAMT, not sign implied by TRNTYPE. HOLD interpretation is account-dependent (§11.4.4.3, pp. 219–220).
- **Account context:** §§11.3.1–2 (pp. 187–191) require bank BANKID/ACCTID/ACCTTYPE with optional BRANCHID/ACCTKEY; card requires ACCTID with optional ACCTKEY and is unique within an institution. §§11.4.2.2 and 11.4.3.2 (pp. 208, 212) permit posted and pending lists in both bank and card responses.

OFX does not supply `before_first`/`after_last` balance roles or arbitrary download completeness.
