# The Analysis Boundary and Tabular Contract

This page specifies the full-system interface between `jbt` and an independent analysis product. [Target architecture](./target-architecture.md) owns the pipeline; this page owns the published tables, their reader contract, and the separation between neutral reference models and analysis policy.

## Ownership and technology

`jbt` publishes reconciled, traceable financial facts, including economic booking and its evidence. Tax, investment performance, planning, jurisdictional lot selection, and valuation policy belong to the analysis product. The interface is a versioned artifact, not a Python import or a rendered ledger. A ledger rendering can choose one date, net fees or withholding, discard the original foreign amount, or omit broker lot identities; analysis must not reconstruct those facts from that projection.

**Parquet is the sole tabular publication format.** Each snapshot contains one immutable, unpartitioned `<table>.parquet` file per table below, including typed empty tables, plus its schema and manifest. The publication root is `out/tabular/`; a manifest identifies a complete snapshot rather than a mutable collection of independently replaced files. Full-system schema representability and conformance fixtures precede runtime slices; processors can be implemented incrementally without postponing the investment, obligation, action, or analysis contracts. A restricted processor set declares its supported inputs and cannot claim to have processed unsupported events.

Parquet provides an open, independently readable, typed columnar container with compression, column projection, and row-group statistics. It avoids CSV type inference without requiring a running database. Financial decimals use the exact representation below, not a reader-dependent numeric guess. A second SQLite or SQL-backed sink would duplicate conformance, migration, and determinism surfaces without adding information. Consumers can export a database themselves. Partitioning requires measured need, not an assumed warehouse scale.

**DuckDB is the reference query engine; dbt with `dbt-duckdb` owns downstream SQL transformations, dependencies, documentation, and tests.** DuckDB reads the Parquet files directly; there is no warehouse service or mandatory import database. dbt does not parse statements, reconcile overlapping sources, or book economic lots upstream. Nor is it required to read the artifact: another implementation can follow this contract without `jbt`, DuckDB, or dbt. These technology choices do not prescribe a household's financial policy.

## Shared type and identity rules

The notation below defines fields, not illustrative suggestions. `S` is NFC-normalized UTF-8 STRING; `I` is signed INT64; `B` is BOOLEAN; `D` is Parquet DATE; `L` is a sorted, duplicate-free LIST of non-null strings; `N` is the exact decimal field group defined below. `?` means nullable; every other field is required. Empty lists are valid and never null. Null, zero, and empty string are distinct; identifiers cannot be empty. No floating-point field is permitted.

Every table has required `entity_id:S`, including `commodity_symbols` and `build`. Every primary key and foreign key includes `entity_id`; local IDs from different entities may coincide. In each table below, `PK` identifies the remaining primary-key fields. Unless a different order is stated, rows sort by the complete primary key, ascending by UTF-8 bytes for strings and by value for other types. Null sorts before non-null in additional sort fields; the primary key is always the final tie-breaker. IDs remain stable across builds when the identified record remains the same; physical row numbers and display names are not identities.

Fields named `account_id`, `category_id`, `commodity_id`, `position_id`, `statement_id`, `txn_id`, `posting_id`, `step_id`, `lot_id`, `pool_id`, `allocation_id`, `change_id`, `action_id`, `counterparty_id`, `source_record_id`, and `declaration_id` reference their corresponding tables. Prefixed variants such as `quote_commodity_id` reference the same dimension. All referenced IDs must exist in the snapshot unless explicitly declared external manifest references. Optional references are null, not dangling. Other reference forms and compound uniqueness constraints are specified with their tables. [ADR 0008](../adr/0008-canonical-economic-identity.md) defines stable economic IDs; ordering indexes never identify records.

Required combinations apply in addition to column nullability. Finite validity intervals have start strictly before end; inclusive statement periods have start no later than end; account closure cannot precede opening. Registries and embedded JSON payload schemas ship with the versioned schema, including their accepted values and numeric units. Financial values inside those payloads use the same exact coefficient/scale representation as table fields, not JSON floating-point numbers.

### Exact decimals and query arithmetic

Every logical numeric field `x:N` expands to `x_coefficient:S`, `x_scale:I`, and `x_source_scale:I?`. Its value is the signed integer coefficient multiplied by 10 to the power of negative scale. Coefficients contain decimal digits, an optional leading minus, no leading zeros, and no negative zero. Value encoding removes trailing coefficient zeros while scale is positive; zero has coefficient `"0"` and scale `0`. Scale is nonnegative. Thus a stated `84.20` has coefficient `"842"`, scale `1`, and source scale `2`. Source scale records the asserted precision independently of normalized value scale. Null source scale means it was not stated; derived values do not inherit fictitious source precision.

For `N?`, coefficient and scale are either both present or both null; source scale is null when the value is null. The same representation covers amounts, quantities, costs, prices, ratios, rates, fees, and contract multipliers. Schema version 1 supports coefficients of at most 96 digits excluding sign, normalized scales from 0 through 38, and source scales from 0 through 38. These resource limits are published in the schema and validated before allocating expanded representations. Inputs outside them fail publication; truncation, saturation, and rounding to fit storage are prohibited. Within this domain every finite decimal is exact using ordinary Parquet strings and integers. The source record remains traceable when normalized numeric encoding omits lexical details. [ADR 0011](../adr/0011-bounded-exact-arithmetic.md) gives the capacity rationale and operation-admission rules.

The reference query profile exposes checked `DECIMAL(p,s)` views for each model's required operations, with `p <= 38`. Before casting, it checks every value is representable without rounding. Before execution, it checks the intermediate bounds for scale alignment, multiplication, and aggregation, including group size and accumulator limits. SQL execution must also fail on overflow. A cast that succeeds for each operand does not establish that the expression is safe: 10^11 units multiplied by 10^9 per unit yields 10^20, which does not fit `DECIMAL(38,18)`.

Addition and multiplication are exact when these checks pass. Ordinary DuckDB `/`, floating-point aggregates, and implicit float promotion are forbidden for financial measures. Division and expressions outside DuckDB's decimal range execute in exact-integer Python UDFs registered with the consumer's local DuckDB connection by the downstream `dbt_jbt` package. These functions use only Python standard-library integers, coefficient strings, and integer scales at the SQL boundary; they do not import `jbt`, accept floats, or return floats. This is an arithmetic helper, not a second transformation orchestrator, and an independent consumer can implement the same integer operations without that package.

The exact-integer profile permits intermediate coefficients, numerators, and denominators of at most 384 decimal digits and intermediate scales from 0 through 152. It checks bounds before expansion and after arithmetic; exceeding them fails the calculation rather than falling back to approximate arithmetic. Published `N` results must fit the 96-digit/38-scale domain. Quotient and remainder implement the model's explicit result scale and rounding mode. For nonterminating results such as 1 ÷ 3, retain an exact numerator/denominator until that declared rounding point. Models pin and test this profile; rounding is a policy-visible operation, never an incidental storage conversion. The pipeline and independent consumer implement the same arithmetic contract, without requiring the consumer to import pipeline code.

### Dates and time

The date bundle is `date_authorized:D?`, `date_traded:D?`, `date_posted:D?`, `date_settled:D?`, and `date_value:D?`. A transaction has no primary date. Null means unknown, not equal to another date. A posting carries the same fields plus one `<date_field>_mode:S` for each: `inherit`, `value`, or `unknown`. Only `value` permits and requires a non-null date. `inherit` reads the corresponding transaction field; `unknown` explicitly prevents inheritance. This distinguishes an absent leg override from an explicitly unknown leg date.

The time bundle is `timestamp_date:D?`, `timestamp_local:S?`, `timestamp_offset_minutes:I?`, `timestamp_zone:S?`, `timestamp_precision:S?`, and `timestamp_fraction_digits:I?`. `timestamp_local` is an ISO wall-clock time, without date or zone, in `HH:MM`, `HH:MM:SS`, or `HH:MM:SS.fraction` form. Its string encoding preserves precision beyond a database's timestamp resolution. Precision is `date`, `minute`, `second`, or `fractional_second`. A present bundle requires a date and precision; `date` has no time, offset, or fraction digits; timed forms require a matching time, with fraction digits required only for `fractional_second`. A zone may accompany a date-only observation without turning it into an instant.

An explicit offset establishes a timed observation's instant. A zone-only wall clock additionally needs a recorded IANA time-zone database version and ambiguity/nonexistent-time rule before conversion. Offsets and named zones are retained independently; disagreement is diagnosed, not silently rewritten. Unspecified time remains unspecified. Date-only valuation declares a civil zone and opening/closing convention rather than inventing midnight UTC.

Transaction and posting times use `event_times`, so authorization, trade, and settlement instants cannot overwrite each other in one timestamp field. Assertions, prices, actions, and book steps each have one explicit temporal purpose and carry their own time bundle. Original competing temporal observations remain evidence even when one canonical value is selected.

## Table contract

The tables below cover evidence, identities, and authoritative determinations. Postings describe economic legs; book steps, inventory allocations, and reference changes describe the decisions needed to replay them. These are not alternative holdings feeds or daily snapshots. Every listed table is required, including when empty.

### Transactions and postings

**`transactions`** — one row per canonical transaction. PK `txn_id:S`; sort `(entity_id, date_posted, txn_id)`.

| Fields | Contract |
| --- | --- |
| Date bundle | Stated or explicitly derived values, with provenance; timed values resolve through `event_times` |
| `event_kind:S` | `transaction`, `opening`, `corporate_action`, or `note`; opening is initialization, not income or a contribution |
| `event_state:S` | `pending`, `recognized`, `cancelled`, or `retracted`, resolved under [ADR 0009](../adr/0009-event-participation-and-replay.md) |
| `payee:S?`, `narration:S?`, `description_as_stated:S?` | Canonical enriched text remains distinct from source text |
| `review_state:S` | `reviewed`, `unreviewed`, `ignored` |
| `tags:L`, `links:L` | Link IDs resolve to `links`; tags are labels, not identities |

A transaction may reconcile several source records. There is no scalar authoritative `statement_id`, `input_kind`, or `source_blob_digest` on its header: join `provenance` to `source_records` for all contributing inputs. Different descriptions and source statuses remain observations. `ignored` is a review label and never suppresses a recognized effect. Notes have declaration provenance and no financial postings. Every holding initialization uses a recognized opening event and posting; `opening_lots` supplies prior acquisition facts, not a second movement.

**`postings`** — one row per economic leg, not per lot match or fee allocation. PK `posting_id:S`; sort `(entity_id, txn_id, posting_index, posting_id)`; `(entity_id, txn_id, posting_index)` is unique. `posting_index:I` is nonnegative and contiguous within a transaction.

| Fields | Contract |
| --- | --- |
| `txn_id:S`, `commodity_id:S`, `amount:N` | Amount is signed units of the commodity; debits positive, credits negative |
| `account_id:S?`, `category_id:S?` | Position legs require an account and no category; boundary legs have no account and may have a category |
| `step_id:S?` | Required for recognized financial legs; null for legs of pending, cancelled, or retracted events |
| Date bundle and override modes | Resolve each effective date independently |
| `posting_role:S` | `principal`, `commission`, `fee`, `tax_withheld`, `accrued_interest`, `variation_margin`, `funding`, `borrow_fee`, `cash`, `collateral`, `book_result`, `rounding` |
| `leg_kind:S` | `position` or `boundary`; a null boundary category is explicitly unclassified, never a fictitious account |
| `position_id:S?` | Required for position legs, null for boundary legs; its account and commodity must match the leg |
| `symbol_as_stated:S?` | Source symbol, not the instrument key |
| `broker_lot_id:S?` | Source label only; multiple stated labels remain observations, not an overwritten scalar |
| `price_per_unit:N?`, `price_commodity_id:S?` | Leg conversion rate and quote commodity occur together |
| `original_amount:N?`, `original_commodity_id:S?` | Original foreign amount and commodity occur together |
| `fx_rate_as_stated:N?`, `fx_base_commodity_id:S?`, `fx_quote_commodity_id:S?` | Stated units of quote per base; all three occur together |

Every source-stated numeric has its own source scale through `N`. Converted amount, original amount, and institution-stated exchange rate are independent observations: deriving one from the others loses the institution's rounding. Source unit costs and totals remain typed observations; exact booked totals live in inventory changes, monetary weights, and disposals. There is no scalar model lot or booked unit cost on a leg that can span several origins. A direction-reversing source fill becomes distinct closing and opening economic legs with source provenance and stable child keys, not two indistinguishable copies of the fill. Category assignment changes classification, not economic identity or participation; outputs requiring complete categorization reject unclassified boundary legs.

**`event_times`** — one canonical temporal role on a transaction or posting. PK `(record_kind:S, record_id:S, date_role:S)`. Fields: `time_mode:S`, plus the time bundle. Record kind is `transactions` or `postings`, with record ID that table's scalar local key. Date role is `authorized`, `traded`, `posted`, `settled`, `value`, or `occurred`; occurred preserves an unqualified source event time without assigning it to a different date role. Time mode is `value` with a present bundle, or `unknown` with an entirely null bundle. A qualified role's timestamp date must agree with its effective date-bundle field. A posting inherits the transaction's qualified time only when its corresponding date mode is `inherit` and no posting time row exists; explicit unknown or an overridden date never borrows a time. Unqualified occurred times are not inherited. A date-only observation remains date-only.

**`book_steps`** — one atomic domain operation in the complete entity replay. PK `step_id:S`; sort `(entity_id, sequence, step_id)`; `(entity_id, sequence)` and `(entity_id, txn_id, step_key)` are unique. Fields: `txn_id:S`, `step_key:S`, `sequence:I`, `operation_kind:S`, `effective_date:D`, plus the time bundle. Step key is the stable semantic operation key within the event; step ID is a domain-separated hash of entity, canonical event ID, and that key, never sequence or mutable quantities. Sequence starts at zero and is contiguous. Operation kind is `opening`, `acquisition`, `reduction`, `transfer`, `pool_entry`, `pool_exit`, `action`, `reference_reset`, `quantity`, or `boundary`. The event must be recognized. A step's effective date is its resolved economic date, not an invented substitute for an absent source date. It has no implied midnight.

**`book_step_dependencies`** — one economic precedence constraint. PK `(before_step_id:S, after_step_id:S, constraint_kind:S)`. Fields: `declaration_id:S?`. Kind is `effective_time`, `source_sequence`, `causality`, or `decision`; decision requires an ordering declaration, and other kinds retain the relevant source/derivation provenance. All edges point forward in the published sequence and the graph is acyclic. Each noncommutative ordering has an evidenced path. Unconstrained steps may use stable-ID tie-breaking only after the model has established that swapping them preserves state and results; this commutativity check travels with the build checks.

Steps carry already determined changes. Sequence is the replay order, not a stable identity or a universal settlement-date order. Readers apply each step atomically, aggregating its deltas before checking resulting state. Source-order constraints, causality, and same-inventory noncommutative operations cannot be reordered by a digest. Per-leg dates continue to govern source reconciliation and explicitly parameterized quantity projections. A booked-inventory as-of cut must be a dependency-closed prefix; an incompatible date basis cannot quietly create a different booking. Pending/cancelled/retracted legs remain inspectable but have no weights, allocations, or reference changes.

**`posting_weights`** — one monetary component used to balance a recognized posting. PK `(posting_id:S, component_key:S)`. Fields: `weight_kind:S`, `amount:N`, `commodity_id:S`. Kind is `principal`, `capitalized_fee`, `expense`, `consideration`, `book_result`, or `rounding`. Amount is a signed accounting weight, not necessarily the posting's instrument units. Weights sum to zero per complete economic event and weight commodity under its event-specific equations. A zero-weight non-cash action or reference opening has no invented notional weight. Capitalized fee weight belongs to the acquiring inventory leg; an observed fee leg is not also weighted as an expense. Field provenance connects each weight to the component and allocation that determined it.

For a disposal, matched economic book cost, proceeds, and a separately identified `book_result` leg balance in the declared book currency. Without fees, reducing a holding carried at 100 and receiving 120 produces signed book weights of -100, +120, and -20. The last component is a neutral derived economic result, not a taxable gain, an additional cash receipt, or an external portfolio flow. It retains booking provenance and uses the same exact arithmetic checks. Explicit fee and rounding legs remain separate; a renderer does not invent an unexplained balancing plug.

Fees, commissions, withheld tax, and interest are separate legs, never netted invisibly into principal. A dividend of 100 with tax withheld of 15 and cash received of 85 retains all three quantities. Liability principal, accrued interest, collateral, contract quantity, contract notional, and settlement cash are distinct. Contract multipliers are never folded into extracted units; a stated notional is an observation, not an invented holding. [ADR 0002](../adr/0002-position-taxonomy.md) owns position semantics.

**`positions`** — one declared holding relationship, not a quantity snapshot. PK `position_id:S`. Fields: `declaration_id:S`, `account_id:S`, `commodity_id:S`, `position_kind:S`, `counterparty_id:S?`, `measurement_kind:S`, `inventory_method:S`, `purpose:S`, `terms_declaration_id:S?`. Position kind is `property`, `claim`, or `contract`; claims and contracts require a counterparty and property has none. Measurement is `cost`, `reference`, or `quantity`; reference is valid only for contracts. Inventory method is `individual`, `pooled`, or `quantity`; quantity measurement and method occur together, and reference positions are individual. Purpose is `general` or `collateral`. Terms reference the effective `contract_terms` revision where needed, including a position-specific agreement rather than an instrument default. Book denomination belongs to the lot or pool, not the position identity; different acquisition currencies do not invent different custody relationships.

The declaration supplies a stable relationship key and source bindings. Multiple positions may share account, commodity, or counterparty; distinguish them only when evidence or a declaration establishes a real separate holding relationship. Free cash and collateral, different lenders, and property versus a custody claim must not be netted merely because they use one currency. A changed counterparty or custody relationship creates a new position and an evidenced movement, not a renamed historical position. A corrected interpretation requires review. The account remains the statement boundary.

### Inventory allocations and exact components

[ADR 0010](../adr/0010-authoritative-inventory-allocations.md) separates economic legs from booking allocations. The replay state is keyed by `(position_id, lot_id)` for individual inventory and `(position_id, pool_id)` for pooled inventory. A lot can occupy several positions after a partial transfer. Quantity-only positions fold recognized postings directly and never acquire fictitious cost lots.

**`lots`** — one acquisition root or successor branch. PK `lot_id:S`. Fields: `commodity_id:S`, `creation_step_id:S`, `origin_posting_id:S?`, `parent_lot_id:S?`, `origin_key:S`, `acquisition_date:D?`, `book_commodity_id:S?`. A root requires an acquisition/opening posting and no parent; a successor requires a parent and no new acquisition posting. Origin key is the stable source-origin discriminator or declared successor role, not a current row number. Parent edges are acyclic. A multi-output action creates a separate branch for each output of each predecessor; it never combines predecessor origins into one invented acquisition. A simple quantity split preserves the lot ID. Distinct branches also distinguish partial contract resets with different remaining references. Acquisition date is the evidenced original date selected under the declared acquisition-date convention, null when unknown; successors inherit it exactly. Opening roots take it from opening evidence, not their initialization date. Book commodity is required for cost measurement and null for reference measurement; transfers and successor branches preserve it.

**`opening_lots`** — prior acquisition evidence for one root initialized by an opening posting. PK `lot_id:S`. Fields: `declaration_id:S`, `broker_lot_id:S?`. The root's posting belongs to an opening event. Units and exact principal/fee totals are initialized once through that posting's inventory allocation, not added from this table. Unknown acquisition dates or components remain unknown; coverage start is not an acquisition date. Original fee currencies and any conversion remain observations and declaration provenance.

**`inventory_pools`** — one declared economic pool, not a synthetic acquisition. PK `pool_id:S`. Fields: `position_id:S`, `declaration_id:S`, `book_commodity_id:S`. The position is cost-measured and pooled. The declaration fixes eligibility, book denomination, fee treatment, effective applicability, and contribution/reduction arithmetic. Contributions in unlike book currencies require a published conversion, never an untyped sum. A policy change that changes pool meaning requires explicit pool exit/entry with continuity checks, not an overwritten identity. Pools have no invented acquisition date.

**`inventory_allocations`** — one authoritative allocation from at most one source inventory slice to zero or more destinations. PK `allocation_id:S`. Fields: `step_id:S`, `allocation_kind:S`, `method_declaration_id:S`, `action_id:S?`. Kind is `acquisition`, `opening`, `reduction`, `transfer`, `pool_entry`, `pool_exit`, or `transformation`. Source and target changes are its children. Separate source origins require separate allocations even when their postings or destinations are shared. An action reference is required for a corporate-action application and otherwise null. Contract exercise or another evidenced lifecycle transformation is identified by the step's event and declared terms rather than mislabeled a corporate action.

**`inventory_changes`** — one signed change to an inventory slice within an allocation. PK `change_id:S`. Fields: `allocation_id:S`, `change_role:S`, `posting_id:S`, `position_id:S`, `lot_id:S?`, `pool_id:S?`, `units_delta:N`, `principal_delta:N?`, `capitalized_fee_delta:N?`, `expensed_fee_delta:N?`. Role is `source` or `target`; exactly one of lot/pool is present. Position, posting, and allocation step agree. Lot commodity matches position commodity; pool position matches exactly. A pooled position may temporarily contain origin lots during contribution operations, but has no individually held remainder at a completed step boundary.

For cost measurement, component deltas use the lot/pool's book commodity and are signed changes, not unit prices. Carrying-cost delta is principal plus capitalized fees; expensed fees are attribution only. Null means the component is unknown; zero means known zero. Unknown state propagates and blocks any determination needing it. Reference-measured inventory has all three component deltas null; fee attributions travel separately rather than altering the reference. A source change removes the signed units and component slice actually held: closing a negative claim therefore has positive unit and principal deltas. A full close consumes all remaining components, including rounding residuals.

| Allocation | Shape and conservation |
| --- | --- |
| Acquisition/opening | No source, one root-lot target; preserves exact consideration and fee totals; opening evidence is not a purchase |
| Reduction | One source, no target; consumes available lot or pool units and exact components; one disposal row records its consideration |
| Transfer | One source and one target per allocated slice; same lot across positions, or explicitly linked pools; units and each component sum to zero in a compatible denomination; no disposal or book result |
| Pool entry | One root/branch source and one pool target in the same position; quantities conserve and components agree in the pool denomination through any explicit conversion; preserves origin without pretending it remains individually held |
| Pool exit | One pool source and one successor-pool target; preserves pooled lineage and exact components, never fabricates an individual acquisition |
| Transformation | One source and one or more targets; declared ratios and component equations govern each output; cash consideration uses linked postings/disposals, not a second receipt |

For each recognized inventory posting, sum its change rows' units to the posting amount. This also covers zero-unit basis adjustments. All changes of a step apply atomically. For a split, remove the pre-split slice and add the transformed slice under the same lot; the net change equals the action posting, not a second application of its ratio. For a spinoff, remove the affected parent slice and create predecessor-specific successor branches. Pool actions operate on pool slices and successor pools; the contribution graph preserves their roots. Apply event equations to component totals, not rounded per-unit products.

Pool reductions consume the declared fraction of aggregate principal and fee components, with deterministic residual allocation. They name the pool, not a constituent acquisition. Pool history consists of its contributions, reductions, and inter-pool transfers; tracing those allocation edges recovers contributing origins and acquisition evidence but does not claim which original physical units remain. An invested feed handoff maps this pool history as well as remaining quantities and components. Tax rematching uses the original acquisition/transfer/action stream and its own policy, not fictitious economic constituent matches. Changing from pooled to individual measurement without sufficient remaining-origin evidence is unsupported, not an automatic pool exit.

**`component_conversions`** — an explicit book-denomination conversion within a pool-entry allocation. PK `(allocation_id:S, component_kind:S)`. Fields: `source_amount:N`, `source_commodity_id:S`, `target_amount:N`, `target_commodity_id:S`, `rate:N`, `method_declaration_id:S`. Component kind is `principal`, `capitalized_fee`, or `expensed_fee`. Amounts describe the same signed contribution before and after conversion; they reconcile to the negated source delta and target delta. Rate is target units per source unit; the declaration and provenance identify date, rate evidence, result scale, rounding, and residual. Same-denomination allocations have no conversion rows. Unknown components cannot be converted as zero. This preserves original basis currency while making the pool determination independently checkable.

**`disposals`** — one allocation's realized consideration and disposal fees. PK `disposal_id:S`. Fields: `allocation_id:S`, `proceeds_total:N?`, `proceeds_commodity_id:S?`, `disposal_fees_total:N?`, `fee_attribution_declaration_id:S`. Allocation is unique across disposals and is a reduction or a transformation with a realized component. Selected source lot/pool, economic date, units, and exact components resolve through its changes. Released book components are the negated sum of source and target component deltas: a transformation that removes basis 100 and retains 70 in successors releases 30, not 100. Its disposal row does not assert that every surrendered unit was sold for cash. A pure reduction has no target and releases its full consumed slice.

Proceeds amount/currency occur together; fees are in that currency, null if unavailable. Proceeds are signed consideration received (negative when paid to close an obligation); fees are signed expense amounts (negative for a rebate). A reference close records only its unsettled settlement here, not the opening-to-closing total already settled. Its reference-change settlement attribution reconciles to the same proceeds, not another cash movement. No duplicate per-unit basis is authoritative.

**`fee_allocations`** — one original fee attribution to an acquisition root or disposal. PK `fee_allocation_id:S`. Fields: `fee_posting_id:S?`, `opening_declaration_id:S?`, `target_kind:S`, `target_id:S`, `amount:N`, `commodity_id:S`, `book_amount:N?`, `book_commodity_id:S?`, `treatment:S`, `method_declaration_id:S`. Exactly one fee source is present: an existing fee leg or evidenced opening-lot fee declaration, never a fabricated historical payment. Target kind is `lot` or `disposal`; lot targets are roots. Amount is the signed allocated portion in the fee's original commodity. Book amount/currency occur together and retain conversion evidence and rounding through provenance. Treatment is `capitalized`, `expensed`, or `attribution_only`; reference lots prohibit capitalization. Original allocations sum to the fee source total. A method may explicitly declare non-attribution; this is not a zero fee and blocks outputs requiring complete attribution.

**`inventory_fee_changes`** — one original-fee slice moving with an inventory change. PK `(change_id:S, fee_allocation_id:S)`. Fields: `amount_delta:N`, `book_amount_delta:N?`. Only lot-targeted original fee allocations participate. Original-currency deltas preserve fee identity through transfers, splits, successors, and pool consumption; book deltas use the changed lot/pool denomination when cost-measured. Cost-measured sums by treatment agree exactly with the inventory change's capitalized/expensed fee deltas, including explicit pool conversion. Reference-measured book deltas are null, while original fee amounts remain attributable through partial closes without changing the contract reference. A reduction removes its acquisition-fee slice; this is attribution, not another expense or disposal fee. Pool attribution follows declared pro-rata component allocation, not a claim that a constituent acquisition was selected. Missing fee evidence remains unknown in the parent components/completeness checks; absent rows do not establish zero.

Exact principal, proceeds, and fee totals are sufficient to derive optional per-unit views under a declared result scale. A total of 10 on three units remains 10. Neither those views nor fee attribution creates another posting. [ADR 0003](../adr/0003-booking-and-lot-identity.md) and [ADR 0004](../adr/0004-lot-selection-rebinding.md) govern selection and guards; jurisdictional rematching never overwrites these determinations.

### Contract reference transitions

**`reference_changes`** — one entry, reset, or close of a reference-measured lot slice. PK `reference_change_id:S`. Fields: `step_id:S`, `position_id:S`, `lot_id:S`, `change_kind:S`, `units:N`, `reference_before:N?`, `reference_after:N?`, `settlement_reference:N?`, `reference_commodity_id:S`, `terms_declaration_id:S`. Kind is `entry`, `reset`, or `close`. Entry has only after, reset has both, close has only before. Settlement reference retains the price/reference used for the settlement calculation, required when the terms use one; it is not a new open position after close. Units are the signed affected contract units, not multiplied notional. Before must equal the current recorded reference for that slice. A partial close preserves the remaining reference. A partial reset splits inventory into named branches before assigning distinct references; one slice cannot have two current references. Transfers carry the reference to the destination slice through paired close/entry transitions without gain settlement.

**`reference_settlements`** — attribution of existing cash settlement to a reference transition. PK `(reference_change_id:S, settlement_posting_id:S)`. Fields: `amount:N`, `commodity_id:S`. Amount is signed cash received in that posting's commodity. Attributions sum to each designated settlement posting and obey the contract-specific formula, multiplier, denomination, and rounding policy. One settlement may span several lots. Entry or custody-transfer transitions have no settlement attribution unless the event separately evidences one. Collateral-only movements have no reference reset. Reset from 100 to 103 with multiplier 10 settles 30; close at 105 settles 20 against reference 103. The opening fact 100 remains at entry, and cash totals 50, not 80.

### Balances, prices, and actions

**`assertion_scopes`** — one explicit measurement scope within a reconciliation account. PK `scope_id:S`. Fields: `account_id:S`, `declaration_id:S`, `scope_kind:S`, `measurement:S`, `coverage_basis:S`, `selection:S`, `position_ids:L`. Scope kind is `positions` or `account_net`; measurement is `units` or `value`. Selection is `account_all` with an empty position list, or `positions` with a nonempty list of positions in that account. The declaration fixes any quote denomination and valuation evidence needed for value checks. Coverage basis supplies recognition and boundary conventions, not an encoded counterparty or ownership share. An all-account scope includes every applicable declared/model position, including a holding absent from the source list.

**`balance_assertions`** — one source assertion set, including an explicitly complete empty set. PK `assertion_set_id:S`; sort `(entity_id, scope_id, date, assertion_set_id)`. Fields: `scope_id:S`, `date:D`, `assertion_kind:S`, `is_complete:B`, `statement_id:S?`, plus the time bundle. Assertion kind is `opening`, `closing`, or `point`. Account, measurement, position selection, and recognition basis come from the scope. An associated statement must agree with that account and basis.

**`balances`** — one measured observation in an assertion set. PK `balance_id:S`; sort `(entity_id, assertion_set_id, position_id, commodity_id, balance_id)`. Fields: `assertion_set_id:S`, `position_id:S?`, `commodity_id:S`, `amount:N`. Position scopes require a position in the scope and uniqueness of `(entity_id, assertion_set_id, position_id)`; for units its commodity must match. Account-net scopes require null position and uniqueness of `(entity_id, assertion_set_id, commodity_id)`; unit totals net only like commodities. Value observations use the declared quote commodity, never pretend to be instrument units.

Complete means every measured position, or every net commodity for account-net scope, is enumerated within that scope. Missing members imply zero only for that measurement. Partial sets say nothing about omissions. A complete +100 USD claim against X and -40 USD obligation to Y has two position rows; a net assertion of 60 has one account-net row and cannot certify either gross holding. Model checks repeat the same scope and measurement. They may report a value check not evaluable for lack of valuation evidence without changing a unit assertion. Opening/closing conventions remain source facts; a renderer's next-day conversion is separate. Coverage and independent assertion evidence must establish sufficiency before analysis uses a balance as a valuation boundary.

**`prices`** — one distinguishable quote observation, not one arbitrary winner per day. PK `price_id:S`; sort `(entity_id, commodity_id, quote_commodity_id, date, price_id)`. Fields: `commodity_id:S`, `quote_commodity_id:S`, `date:D`, `rate:N`, `basis:S?`, `origin:S`, `market:S?`, plus the time bundle. Basis is `close`, `open`, `mid`, `bid`, `ask`, `nav`, `trade`, `mark`, `index`, or `settlement`; null means unstated. Origin is `extracted`, `authored`, or `derived`; provenance identifies the source or explicit derivation. Rate means quote units per one commodity unit, before any declared contract multiplier.

Different markets, times, sources, and bases remain distinguishable. A source basis outside the accepted set remains an observation until explicitly mapped; it is not silently labeled close. Consumers declare market calendar, freshness, quote basis, action-relative timing, and FX conversion policy. A missing suitable price blocks that valuation, not publication of faithful transactions.

**`corporate_actions`** — one event identity. PK `action_id:S`; sort `(entity_id, effective_date, action_id)`. Fields: `action_kind:S`, `commodity_id:S`, `effective_date:D`, `announcement_date:D?`, `record_date:D?`, `payment_date:D?`, `txn_id:S`, plus the time bundle. Kind is `split`, `reverse_split`, `merger`, `spinoff`, `stock_dividend`, `return_of_capital`, `redenomination`, or `symbol_change`. Its transaction carries participation state and has `event_kind=corporate_action`. `commodity_id` is the affected instrument; multiple event sources attach through provenance.

**`corporate_action_effects`** — one stated or declared input/output term of an action. PK `effect_id:S`; sort `(entity_id, action_id, effect_index, effect_id)`. Fields: `action_id:S`, `effect_key:S`, `effect_index:I`, `effect_kind:S`, `input_commodity_id:S`, `resulting_commodity_id:S?`, `ratio_numerator:N?`, `ratio_denominator:N?`, `cash_per_unit:N?`, `cash_total:N?`, `cash_commodity_id:S?`, `basis_per_unit:N?`, `basis_total:N?`, `basis_commodity_id:S?`, `symbol_id:S?`, `scope_declaration_id:S?`. Both `(entity_id, action_id, effect_key)` and `(entity_id, action_id, effect_index)` are unique. The stable effect key names an output role; index is serialization only.

Effect kind is `units`, `cash`, `basis`, or `symbol`. Units requires a resulting commodity and positive ratio pair, defined as resulting units per input unit. Cash/basis requires its commodity and at least one of per-unit or total; a stated total requires an explicit scope. Preserve both when stated, and diagnose discrepancies rather than replacing either. Symbol requires a `commodity_symbols` reference. Unrelated fields are null. `action_scope` declarations identify account/position/lot/pool eligibility for the input commodity; null scope means instrument-wide terms. Effects describe terms, not applied movements. A basis term is source-stated or explicitly declared economic policy, not a jurisdictional allocation by default.

**`action_applications`** — one applied term linked to a booked determination. PK `(effect_id:S, target_kind:S, target_id:S)`. Fields: `step_id:S`, `application_role:S`. Target kind is `inventory_allocation`, `inventory_change`, `disposal`, or `posting`, resolving to that table and its actual step; inventory changes resolve their step through the owning allocation. Role is `inventory`, `consideration`, or `settlement`. A basis effect targets the exact inventory change receiving that basis, not a whole multi-output allocation. Its total, or its per-unit amount multiplied by the targeted change's units, must agree with that change's principal delta; the basis currency must match its book currency. Inventory allocations name the same action; separate cash events connect through evidenced lifecycle/settlement links. Recognition and later cash settlement may have different steps and dates; a separately observed receipt is not forced into the action's original transaction. Multi-output applications may link several effects to one transformation without leaving the affected output ambiguous. Consumers follow recorded deltas, never apply terms a second time. Completeness checks require each eligible slice, consideration, and subsequent settlement exactly once in its role. Symbol-only terms update dated symbol evidence and have no invented financial application. [ADR 0005](../adr/0005-corporate-actions.md) owns action continuity.

### Identity and coverage

**`accounts`** — one stable custody, statement, and reconciliation boundary. PK `account_id:S`. Fields: `declaration_id:S`, `institution:S?`, `opened_date:D?`, `closed_date:D?`, `operating_commodity_id:S?`, `statements_expected:B`, `statement_cadence:S?`, `civil_zone:S?`, `coverage_start_date:D?`. Cadence is `monthly`, `quarterly`, `annual`, or `irregular`. Institution opening date may be unknown; coverage start is a separate, explicit commitment. Expected statements require cadence, coverage start, and civil zone. An irregular cadence additionally references an explicit expected-period schedule in the account declaration. One account can contain assets and obligations in several instruments and never has a mandatory ledger-root type.

**`categories`** — one stable classification of a boundary effect, not a holding or reconciliation account. PK `category_id:S`. Fields: `declaration_id:S`, `name:S`, `category_type:S`, `parent_category_id:S?`. Type is `income`, `expense`, or `equity`. Parent edges are acyclic and preserve type. Renaming or regrouping does not change identity. Categories have no statements, balances, positions, or opening inventory. Renderer declarations map positions and categories separately to sink paths; neither a five-root ledger tree nor a category path identifies the institutional account.

**`commodities`** — one instrument or currency identity, independent of tickers. PK `commodity_id:S`. Fields: `name:S?`, `commodity_kind:S`, `isin:S?`, `cusip:S?`, `quote_commodity_id:S?`, `contract_multiplier:N?`, `terms_declaration_id:S?`, `display_precision:I?`. Kind is `currency`, `equity`, `fund`, `etf`, `crypto`, `contract`, or `other`; `other` is an explicitly declared classification, not a parser fallback. Contract multiplier is positive and required where quoted prices need one; it agrees with the referenced terms, not a second adjustable multiplier. Applicable contract terms are required for contractual instruments, including notes represented as claims. Display precision is nonnegative presentation metadata, never permission to round evidence.

**`counterparties`** — one declared counterparty identity. PK `counterparty_id:S`. Fields: `name:S`, `declaration_id:S`. Institution names are not implicit foreign keys. Contract specifications and account declarations determine which position is against which counterparty.

**`commodity_symbols`** — one dated, source-scoped symbol assignment. PK `symbol_id:S`. Fields: `commodity_id:S`, `symbol:S`, `source_scope_id:S?`, `exchange:S?`, `valid_from:D`, `valid_to:D?`. Sort `(entity_id, commodity_id, valid_from, symbol_id)`. Source scope resolves in the manifest binding map; null means explicitly global. Intervals are half-open; null end is unbounded. Resolve by source scope, exchange, symbol, and date; applicable global and scoped assignments must agree or fail, not silently override. Several aliases can identify one instrument, but one lookup cannot identify several instruments. Symbols do not create or merge instrument identities. These are authored validity intervals, not computed open-lot state.

**`statements`** — one account/period coverage declaration for an acquired or authored input. PK `statement_id:S`; sort `(entity_id, account_id, period_start, statement_id)`. Fields: `account_id:S`, `institution:S?`, `source_class:S`, `period_start:D?`, `period_end:D?`, `stated_currency:S?`, `source_format:S`, `is_eclipsed:B`, `coverage_basis:S`, `declaration_id:S?`.

Source class is `statement` or `rolling`; format is `ofx`, `csv`, `pdf`, `json`, `xml`, or `authored`. Unknown formats require a schema-supported mapping, not an unchecked enumeration extension. Statement periods have both inclusive endpoints; rolling observations may lack one or both and cannot thereby satisfy a missing statement period. `stated_currency` preserves the source token; commodity identity is resolved separately. `coverage_basis` names the manifest's declared finite coverage-basis registry, including the applicable date and balance convention. Authored statements require a declaration and no invented blob; acquired statements have at least one associated source record. `is_eclipsed` means no records contributed after precedence resolution, not that the source was deleted.

Coverage validation runs against the build's committed `as_of`, not the execution clock, and uses the declared cadence, civil zone, start, closure, and expected periods. Complete source observations do not establish coverage outside those periods.

### Evidence, declarations, and relationships

**`source_records`** — one addressable occurrence in acquired bytes and a retained source scope. PK `source_record_id:S`. Fields: `source_blob_digest:S`, `source_scope_id:S`, `source_section:S`, `record_locator:S`, `statement_id:S?`, `input_kind:S`, `external_record_id:S?`. Input kind is `bank_statement`, `brokerage_statement`, `payslip`, `receipt`, `market_data`, or `document`. Blob and source scope resolve in the manifest's vault/binding maps. Scope is the stable reviewed source namespace, not an importer version, accession timestamp, or rendered account name. Reacquiring the same bytes in the same scope does not create another occurrence; identical bytes bound to genuinely distinct source contexts can remain distinct.

Section and format-qualified locator distinguish source records, including repeated source IDs and identical rows; an OFX ID alone is not a locator if reused. Changing the resolved model account need not change source scope. A multi-account source retains its sections in one extraction. A blob can contain many records, and several occurrences can support one canonical transaction. Authored entries belong to `declarations`, not fictional acquired records.

**`declarations`** — one immutable revision of an upstream authored input retained by this snapshot. PK `declaration_id:S`. Fields: `declaration_key:S`, `declaration_kind:S`, `revision_digest:S`, `document_path:S`, `document_locator:S`, `payload_json:S`, `valid_from:D?`, `valid_to:D?`. Declaration key is the stable authored identity; declaration ID identifies its exact revision, allowing historical and active revisions to coexist. Payload is canonical JSON governed by the versioned schema; digest covers its complete typed meaning. Kind is `account`, `category`, `commodity`, `counterparty`, `position`, `assertion_scope`, `action_scope`, `opening_lot`, `booking`, `pool`, `fee_attribution`, `contract_terms`, `corporate_action`, `identity`, `ordering`, `rule`, `correction`, `link`, or `authored_fact`. Intervals are half-open; a null endpoint is unbounded and remains JSON null in revision identity, never an invented date. Applicable revisions must be unique for a key and context; historical revisions remain addressable but cannot override active policy.

The [declaration and registry contract](./declarations.md) owns the closed payload variants, ordering/source-status registries, assignable rule fields, and terms. The manifest identifies effective declaration revisions explicitly; retained historical revisions do not participate merely because they are present. Current targets must resolve; historical targets in superseded/retracted decisions preserve judgement without fabricating a current record. Active corrections still require guard-valid current targets.

Payloads needed to interpret or explain a determination travel with the snapshot. Retained rule/derivation definitions in the manifest reference these declarations and identify their exact algorithms and numeric units; a consumer does not need to import pipeline code or reopen a private checkout.

**`economic_identities`** — canonical anchor and lifecycle of an economic identity. PK `(record_kind:S, record_id:S)`. Fields: `anchor_kind:S`, `anchor_id:S`, `event_key:S`, `identity_state:S`, `decision_declaration_id:S?`. Record kind is `transaction` or `corporate_action`; record ID is that table's local key. Anchor kind is `source_record` or `declaration`, resolving to retained evidence. An authored canonical anchor uses the declaration's stable key, not its revision ID or payload digest. Event key distinguishes separate economic components supported by one source record. State is `active` or `retired`; a retired identity remains addressable but its event is retracted and has no participating book steps. Multiple event observations require an identity decision. Its versioned payload carries complete occurrence/key membership, canonical anchor/key, reviewed facts, and explicit merge/split/retirement references under [ADR 0008](../adr/0008-canonical-economic-identity.md). Supporting observations and declarations connect through provenance. Source authority and event recognition are independent of identity state: an active identity can describe an economically retracted event.

**`observations`** — one source-stated or authored value retained separately from the canonical field. PK `observation_id:S`. Fields: `record_kind:S`, `record_id:S`, `field_name:S`, `observation_kind:S`, `value_type:S`, `decimal_value:N?`, `text_value:S?`, `date_value:D?`, `commodity_id:S?`, `source_record_id:S?`, `declaration_id:S?`. Exactly one evidence reference is present. Value type is `decimal`, `text`, or `date`, with exactly the corresponding payload present; numeric units are specified by commodity or the field schema. Observation kind is `description`, `source_status`, `broker_lot`, `broker_match`, `broker_basis`, `broker_gain`, `notional`, or `source_field`. `source_field` requires a manifest field definition with units and meaning. Source status retains its exact source token as text under `source.status`; it is not the canonical event-state enum. This table preserves competing original descriptions, broker matches, calculations, and unmapped stated classifications without treating them as derived truth. Structured broker matches use the closed canonical JSON text payload in the declaration and registry contract.

**`links`** — one named participant in an N-ary relationship. PK `(link_id:S, member_role:S, member_kind:S, member_id:S)`. Fields: `link_kind:S`, `origin:S`, `terms_declaration_id:S?`. Origin is `derived`, `correction`, or `declaration`. Member kind is `transaction`, `posting`, `blob`, `lot`, or `commodity`, resolving to its table or manifest blob map. All members share kind, origin, and terms revision. Allowed roles and member types are closed:

| Link kind | Roles, member types, and cardinality |
| --- | --- |
| `transfer` | One or more posting `outgoing` and posting `incoming` |
| `card_payment` | One or more posting `payment` and posting `credit` |
| `settlement` | One or more transaction `trade` and transaction `settlement` |
| `document` | One or more transaction/posting/lot/commodity `subject` and blob `evidence` |
| `lot_transfer` | One or more lot `source` and lot `destination`; the same lot may have both roles across custody positions |
| `trade_chain` | One transaction `open`, zero or more transaction `roll` and `close`; members are distinct and replay order supplies chronology |
| `lifecycle` | One or more transaction `predecessor`, zero or more transaction `successor`, posting `cash` and `fee`; a failed attempt with a paid fee need not invent a successor |
| `complete_set` | At least two distinct commodity `outcome` members; required `contract_terms` revision declares the exhaustive outcome set and redemption terms |

Each required role has at least one member unless another count is stated. Optional roles may be absent. Terms are null except for `complete_set`; its members equal the declared outcomes exactly. A lifecycle needs at least a successor, cash, or fee member. Links explain relationships; inventory allocations, not membership, determine transferred slices. A strategy group changes no balances, and a complete-set relation does not merge outcome identities, assume equal probabilities, or create redemption. Links do not authorize cross-entity deduplication or choose a portfolio perimeter.

**`provenance`** — one field-to-evidence edge, allowing multiple edges for the same field. PK `provenance_id:S`; sort `(entity_id, record_kind, record_id, field_name, provenance_id)`. Fields: `record_kind:S`, `record_id:S`, `field_name:S`, `value_origin:S`, `evidence_kind:S`, `evidence_id:S`, `derivation_id:S?`. Value origin is `extracted`, `rule`, `correction`, `declaration`, `booking`, or `action`. Evidence kind is `source_record` or `declaration`, resolving to those tables. Derivation ID references the manifest's retained rule/derivation definition and version; it is required for rule, booking, or action output. Correction output requires correction-declaration evidence as well as retained affected source evidence when acquired.

`record_kind` in observations and provenance is a table name from this contract other than `provenance` or `build`; `record_id` encodes that table's local primary key as a canonical JSON array, including single-column keys. In provenance, `field_name` resolves to the target table's field schema; logical decimal names cover their physical field group. In observations it can also name a manifest-defined observation field, such as a broker gain that has no canonical calculated column. Provenance supplies all contributing leaves and the derivation identity for each extracted, enriched, corrected, or booked semantic field, not a convenient single source. Pure identity keys are explained by record identity rules and need no fabricated extraction edge. Original observations and selected canonical values remain distinct; an inferred value must never appear extracted simply because its inputs came from a statement.

### Build metadata and evolution

**`build`** — one row per entity in the snapshot. PK `entity_id` alone. Fields: `manifest_digest:S`, `producer_version:S`, `schema_version:I`, `schema_digest:S`, `as_of:D`, `execution_fingerprint:S`, `is_dirty:B`. The snapshot manifest lists the participating entities, every build-row field except `manifest_digest`, non-build payload byte digests, table row counts and logical content digests, schemas, declared limits, registries, input/declaration digests, writer settings, toolchain versions, and retained derivation definitions. The build ID, stored as `manifest_digest`, is the lowercase hexadecimal SHA-256 digest of the canonical manifest bytes. The manifest contains neither its own digest nor a `build.parquet` checksum. Only `build.parquet` and the commit descriptor embed the current build ID; other payloads and their embedded file metadata must not contain it.

The manifest also carries the effective declaration revision IDs, supported capability registry, enabled outputs and their required checks, and all scoped check results. Each result has a stable check ID, entity-qualified scope, `pass`/`fail`/`not_evaluable` status, `info`/`warning`/`error` severity, typed expected/observed values, evidence references, and applicable policy/exception declaration references. Their schemas ship with the artifact. Required failures prevent publication; allowed working-record limitations remain visible to readers, and an exception cannot waive structural, identity, or arithmetic corruption. A consumer can therefore check completeness without trusting the mere existence of a published directory.

Checksum order is explicit: first write and hash every non-build payload, including separate schema files; then serialize the manifest as compact NFC UTF-8 JSON with lexicographically sorted keys, integer values encoded as decimal strings, and one final LF, and compute its SHA-256 digest. Next write `build.parquet`, mirroring manifest metadata and adding that digest, and hash its complete bytes. Finally write the commit descriptor containing the manifest digest and all payload checksums, including `build.parquet` but excluding the descriptor itself. Publication checksums use SHA-256; acquired source digests retain their identified upstream algorithms. Publish the descriptor atomically only after validation. Consumers pin its externally computed checksum and verify the manifest and payloads in that order. No checksum dependency leads back to a payload containing the current build ID.

The manifest carries a machine-readable expansion of the fields above, accepted values, nullability, keys, relationships, numeric groups, ordering, and schema version. Readers verify the declared schema before interpreting rows. Schema versions are positive integers independent of producer versions. Once snapshots are supported as durable inputs, a change to fields, types, allowed values, grains, keys, null meaning, arithmetic encoding, or semantics increments the version; a consumer explicitly supports a version and rejects unknown versions rather than inferring compatibility from similar column names. Before that external commitment, revise the implementation baseline with its fixtures and readers when evidence reveals a design flaw. Consumer-owned migrations create new staged relations, not altered historical snapshots.

Publication is atomic: write and validate the entire immutable snapshot, then atomically publish its commit descriptor. Readers select and pin that descriptor once, verify every listed file and reject missing, changed, extra schema-bearing, or mismatched files. They never glob a directory that a producer is concurrently replacing.

Logical financial-content digests are separate from physical file digests and build identity. They include entity membership, committed `as_of`, semantic schemas and registries, source bindings and account mappings (independent of their enumeration order), effective declaration revision IDs, retained derivation definitions, financial check results, and every non-build table's key-sorted typed rows. Manifest `checks` contains financial and model-conformance findings only; byte, file-inventory, and read-integrity results belong to descriptor/reader verification, not that collection. Financial-content digests exclude the `build` table and execution-only metadata: producer/writer versions, execution fingerprint, dirty-tree status, manifest digest, physical file digests and their integrity-check results, and encoding/compression settings. Thus a writer upgrade or another accession of the same evidence can preserve financial content while changing the build ID. Per-row financial provenance, evidence identities, source interpretations, declarations, original scales, and derivation semantics remain compared; exclusion of execution metadata is not exclusion of audit evidence.

Row canonicalization includes schema version and ordered field definitions, then compact UTF-8 JSON arrays: dates use ISO dates, integers and decimal coefficients use canonical base-ten strings, booleans and null retain JSON types, and lists retain their declared order. NFC normalization, explicit type tags from the schema, and one LF after each array make encoding unambiguous. All physical files, including `build.parquet`, still have byte digests verified by the commit descriptor.

Parquet writer metadata, encodings, and compression can change file bytes without changing logical content. Record every writer/library/toolchain version and compression, dictionary, statistics, and row-group setting in the execution fingerprint. None enters the logical row digest merely as producer metadata; all remain part of build identity. Text sinks retain byte comparison under the pinned toolchain.

Retained artifacts permit snapshot comparison. Rebuilding a prior artifact also requires retained inputs, declarations, configuration, dependencies, and the exact toolchain; git commits alone do not preserve external observations. An analysis build pins both the `jbt` snapshot and its own code, declarations, policy versions, and dependency lock. Comparing “as filed” with “as recomputed” is snapshot comparison, not an automatically bitemporal database.

## Consolidation and consumer declarations

Each independently buildable project represents one natural or legal person. Household and dated filing groups are downstream collections of those entities, not replacement project identities. A reconciliation account, its legal title, beneficial ownership shares, and tax attribution are separate relationships: shared title does not establish equal beneficial shares or common filing treatment.

A multi-entity reader takes an explicit registry of snapshot descriptors and entity membership, not a filesystem glob or profile-name convention. Local identities remain entity-scoped. [ADR 0006](../adr/0006-multi-entity-consolidation.md) owns consolidation: the registry records a **user-approved authoritative feed per shared account, period, and basis**. Independently retained owner copies remain valid inputs for comparison; byte equality is not event identity.

For feed authority, basis means the comparable measurement and recognition view, including denomination where relevant: settled versus available cash, trade-date versus settlement-date positions, or economic cost versus source-reported tax basis. It does not mean ownership shares or filing elections. An analysis selects its required view and cannot count the same movement twice because different views have separate authority entries.

Comparable financial conflicts in quantities, amounts, instrument/account identity, dates required by the basis, or basis itself block the consolidated build, even after a preferred feed is selected. Authority does not waive contradictory evidence, and labeling an output uncertified does not permit conflicting feeds to be combined. Explicit presentation differences may be reported without treating them as financial agreement. Authority selects evidence; it does not determine beneficial ownership, portfolio membership, or tax attribution. Consolidated checks repeat domain and table validation after account mapping and authority selection.

This page owns the analysis declaration reader contract. Declarations are versioned, reviewed inputs beside their consumer, with a schema version, stable declaration ID, revision digest, effective interval, and explicit entity-scoped references. A reader validates the complete declaration set before running its selected models: required fields and enumerations, resolvable identities, applicable dates, nonoverlapping authority/policy assignments, and completeness for the question. Unknown fields or versions, ambiguous overlaps, and missing required policy fail that analysis. Optional policy is optional only if no selected model needs it; silence is never an election.

| Declaration group | Required content when used |
| --- | --- |
| Population and attribution | Snapshot descriptors, participating entities/people/accounts, effective periods, account mappings, authoritative shared feeds, beneficial shares, and taxpayer attribution; shares within a declared ownership scope must reconcile |
| Cash flow and performance | Account and asset perimeter, transfer/contribution/withdrawal classification, treatment of income, principal, interest and fees, reporting currency, return method, and external-flow timing |
| Valuation and FX | Boundary date, civil zone, opening/closing convention, price basis, market/calendar, staleness limits, action-relative adjustments, FX source and conversion date, and missing/conflicting-evidence behavior |
| Lots and tax | Jurisdiction, taxpayer and tax periods, lot election/rematching rules, relevant accounts, instrument equivalence, acquisition/disposal fee treatment, action treatment, rounding, and statutory policy version |

Declarations can identify accounts and instruments but cannot change source facts. Missing beneficial ownership cannot be filled from whose feed was selected. Changing tax policy creates a new analysis build, not new economic booking evidence. A jurisdictional declaration must distinguish an actual taxpayer election from a model default required by law. Storage syntax belongs to the analysis project; its validated reader must expose these typed inputs and preserve their revisions.

Reference models owned under [ADR 0007](../adr/0007-derivation-placement.md) resolve posting dates, expose provenance, join identities, project recognized posting roles, and replay recorded allocations and reference transitions into booked inventory and date-scoped series. They neither choose a tax jurisdiction nor quietly impose a valuation, ownership, or performance convention. The versioned `dbt_jbt` reference package lives alongside `jbt` and owns staging, neutral intermediates, and the declaration resolver: parsing, schema checks, identity resolution, and effective-period validation. Private consumers own declaration values and policy marts; a shared reader does not choose those values for them. Consumers pin the package version together with supported input schemas. Question-specific marts start in `pta-analysis-<household-slug>`; jurisdiction packages follow the single [release gate](./project-topology.md#jurisdiction-package-release-gate).

## Analysis layers and report semantics

The analysis project uses `dbt_project.yml`, a local DuckDB profile, `models/staging`, `models/intermediate`, `models/marts`, and `tests`. Dependencies are dbt `ref()` edges, not a separately invented orchestration graph.

| Layer | Responsibility |
| --- | --- |
| Sources | Manifest-pinned Parquet relations and validated declaration inputs |
| `stg_` | One model per source table; names and checked types only, no silent coercion, joins, policy filters, or aggregation |
| `int_` | Reusable joins, effective dates, entity mapping, recorded-allocation/reference replay, and explicitly parameterized as-of positions |
| `fct_`, `dim_` marts | Question-shaped event measures and descriptive dimensions for tax, investing, and planning |

For example, a staging relation can directly project exact amount components without a lossy numeric cast:

```sql
select entity_id, posting_id, txn_id, account_id, commodity_id,
       amount_coefficient, amount_scale, amount_source_scale
from read_parquet('pinned-snapshot/postings.parquet')
```

Marts use `{{ ref('stg_postings') }}` and intermediate relations for dependencies. They do not branch on which bank originated a row. Generic dbt tests cover required fields, composite uniqueness, accepted values, and relationships; singular tests cover cross-model invariants. dbt documentation connects source relations to reported measures; row-level lineage keys and retained declarations connect a reported figure to its evidence. A graph alone does not prove a tax calculation correct.

**Cash flow is not the sum of postings.** Buying goods for 100 creates an expense debit and a cash credit whose sum is zero. Moving 100 from checking to savings also sums to zero but is not spending. Paying 105 on a loan can reduce principal by 100 and incur 5 interest; counting 105 as expense misstates both. A monthly cash-flow mart defines its economic perimeter, resolves leg-specific dates, classifies actual flows across that perimeter, and groups by currency or applies a declared conversion. Opening initialization, non-cash `book_result`, and balancing `rounding` effects are not transfers, contributions, withdrawals, or spending merely because they use a boundary category. Event kind and posting role distinguish them from actual boundary transfers and expenses. The mart does not sum both sides of double entry, infer expense classification from an account-name prefix, or add USD to EUR.

**Valuation is an as-of calculation.** Ten shares marked at 12 are worth 120 in the quote currency; debt of 40 yields net worth 80 only when holdings, debt, price, FX, and time boundaries are compatible. A stale quote or a split between quote and boundary can invalidate that result. Completeness, price freshness, calendar, quote basis, action adjustment, and civil-time convention are declared and checked; absent evidence is surfaced rather than filled with zero.

**Performance is not gain or change in value.** An opening portfolio of 100, contribution of 50 at the start of the period, and closing value of 165 give 10% simple return under that timing assumption, not 65%. Intraperiod contributions require a declared time-weighted, money-weighted, or other method with its required valuations. A lot acquired for 100 with 2 acquisition fees and sold for 120 with 3 disposal fees has a nominal difference of 15 if both fee classes are included in one currency. Tax treatment, FX date, and basis adjustments can yield a different figure.

**Actions have multiple consequences.** A two-for-one split changes ten units to twenty without doubling aggregate economic value. A spinoff creates another instrument and can require a declared basis allocation. Consumers use action effects and actual posted applications without counting both twice or treating a symbol change as a taxable disposal.

**Tax matching is independent of economic booking.** In a simplified US wash-sale example, ten shares bought at 100, sold at 90, and replaced at 95 can defer a loss of 100 and adjust replacement cost from 950 to 1,050. The model needs dated acquisitions and reductions, original cost/proceeds, attributable fees, stable identities, a complete relevant-account acquisition stream, and an analysis declaration of substantially identical instruments. Tax matching can select different acquisitions from `disposals`. The tax mart records its own matches and adjustments and leaves the economic records unchanged.

This example is not a complete tax algorithm: partial replacements, statutory windows, related accounts, exceptions, and holding-period adjustments require a reviewed jurisdictional model. Missing declarations, ambiguous replacements, and untraceable adjustments fail the analysis. A market-value tax regime instead needs period-boundary quantities and suitable prices; its missing valuation input is not an extraction defect.

## Validation and policy decisions

| Owner | Required checks | Failure consequence |
| --- | --- | --- |
| `jbt` domain | Reconciliation, committed-`as_of` coverage, overlap consistency, participation/order, booking completeness, inventory/reference continuity, exact component conservation, action applications | Stop affected local determinations; a pass does not prove evidence exists outside declared coverage |
| `jbt` publication | Exact schema, all tables, physical types, required combinations, closed enumerations, keys/FKs, row order, exact numeric encoding and limits, provenance completeness, atomic manifest/file integrity | Do not publish a conforming snapshot |
| Analysis | Supported snapshot/schema, complete declarations, arithmetic bounds, chosen perimeter and dates, attribution, prices/FX, rematching, report reconciliation and evidence-to-result lineage; repeat scoped continuity and financial checks after consolidation without importing the pipeline | Fail or explicitly qualify the requested report under its declared completeness policy; never silently certify an incomplete result |

A downstream assertion cannot fail an otherwise faithful upstream artifact. Upstream conformance cannot make absent prices, original acquisition evidence, or taxpayer elections exist.

User policy supplies ownership, approved feeds, reporting perimeters, valuation/FX conventions, and jurisdictional elections; it does not supply missing structural semantics. The [step-0 handoff](../plans/delivery.md#0-establish-and-exercise-the-full-contract) records the representation proof: domain determinations have typed carriers, and an independent reader replays compound histories without rebooking. Prose establishes the intended contract; executable examples and conformance checks establish its readiness.
